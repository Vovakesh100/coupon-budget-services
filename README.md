# coupon-budget-service

An HTTP service that issues coupons against campaign budgets. A coupon can be redeemed only while budget remains, and concurrent requests never overspend. Amounts are integers in micro units.

> Status: work in progress. Portfolio demo project.

## Quick start

Requires Docker with Compose.

```bash
cp .env.example .env        # then set POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB
docker compose up --build
```

The stack starts PostgreSQL 16, Redis 7 (append-only file on) and the app on port 8000.
The app applies migrations on start. Check it with `curl localhost:8000/openapi.json`.
Use a password with letters and digits only: it is placed into a URL.

## API

- `POST /campaigns`: create a campaign with a budget
- `POST /campaigns/{id}/coupons`: issue a coupon
- `POST /coupons/{id}/redeem`: redeem a coupon (send `Idempotency-Key`)
- `GET /campaigns/{id}/budget`: budget state

## Architecture

Domain logic has no I/O. Redis and PostgreSQL sit behind interfaces in `ports/`. The budget invariant (`spent <= budget`) is checked by property tests and concurrency tests. See `docs/TZ.md` and `docs/adr/`.

## Known limitations

- Redemption state lives only in Redis. Data outside Redis (campaign and coupon records) is in PostgreSQL. If a write to one store fails after the other succeeded, nothing repairs the gap yet.
- Redis runs as a single instance, not Redis Cluster.
- If Redis is unavailable, requests answer 503 (`budget_store_unavailable`) after the client retries.
- No authentication: the API is for trusted callers only.
- The container health check only proves that the HTTP process answers. It does not check PostgreSQL or Redis.
- Campaign and coupon ids are generated by the server. Clients cannot choose them.
